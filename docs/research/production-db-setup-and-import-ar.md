# ربط قاعدة بيانات Masar وتشغيل استيراد الفرص — دليل تشغيلي

تاريخ الدليل: 17 أكتوبر 2026

## الحالة الحالية المؤكدة

- أُعدّ استيراد PostgreSQL لستة مرشحين رسميين، وكل سجل جديد سيبقى بالحالة `review`.
- اجتاز الاستيراد والملف المرافق للتحقق اختبارات PostgreSQL في قاعدة مؤقتة ضمن GitHub Actions. هذه ليست قاعدة الإنتاج.
- مساحة Render المتصلة لا تحتوي على قاعدة PostgreSQL مُدارة. لذلك لا يمكن اعتبار الفرص مستوردة في الموقع الحي.
- ملف API في `apps/api/src/server.ts` ينشئ اتصال PostgreSQL عند وجود `DATABASE_URL` فقط. عند غيابه تعيد نقطة `/health` الحالة `database: not_configured` ويستخدم `/api/opportunities` بيانات توضيحية بدل قاعدة البيانات.

## 1. تحديد قاعدة البيانات المقصودة

استخدم قاعدة PostgreSQL الدائمة المعتمدة للمشروع إن كانت موجودة لدى مزوّد آخر. لا تنشئ قاعدة جديدة لمجرد إكمال الاستيراد دون تحديد المزوّد وخطة الاحتفاظ بالبيانات.

توثيق Render الرسمي يذكر أن قاعدة PostgreSQL المجانية تنتهي بعد 30 يومًا ولا تدعم النسخ الاحتياطية؛ لذلك ليست خيارًا مناسبًا كمخزن دائم للإنتاج:
- [Render: Deploy for Free — قيود قواعد البيانات](https://render.com/docs/free)
- [Render Postgres](https://render.com/docs/postgresql)

لا ترسل كلمة مرور قاعدة البيانات أو قيمة `DATABASE_URL` في المحادثة أو في commit. احفظها في مدير الأسرار لدى مزوّد الاستضافة أو كمتغير بيئة محلي مؤقت. إن لم تكن قاعدة دائمة موجودة، يلزم اتخاذ قرار مستقل بشأن مزوّد قاعدة البيانات والتكلفة قبل المتابعة.

## 2. فحص الاتصال والوجهة دون تغيير البيانات

من جذر المستودع، بعد ضبط `DATABASE_URL` محليًا في البيئة الآمنة:

```bash
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f db/imports/preflight-official-opportunities-2026-10-17.sql
```

يعرض الملف اسم قاعدة البيانات والمستخدم وإصدار PostgreSQL، ويفحص الجداول الخمسة والإضافتين المطلوبتين (`pgcrypto` و`vector`). هو استعلام قراءة فقط. **تحقق يدويًا من أن اسم قاعدة البيانات والوجهة يخصان Masar المقصود قبل الاستمرار.** لا تكمل إن لم تكن الجداول والإضافات المطلوبة موجودة.

## 3. أخذ نسخة احتياطية قبل الاستيراد

استخدم آلية النسخ الاحتياطي/اللقطة التي يوفرها مزود قاعدة البيانات الفعلية، أو تصديرًا موثوقًا محفوظًا في مكان خاص خارج Git. لا ترفع ملف النسخة الاحتياطية إلى المستودع أو إلى artifact عام. لا تشغّل الاستيراد على الإنتاج قبل التأكد من إمكانية الاسترجاع.

## 4. الاستيراد والتحقق

بعد تأكيد الوجهة وأخذ نسخة احتياطية، نفّذ الأمر التالي من جذر المستودع:

```bash
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f db/imports/official-opportunities-2026-10-17.sql
```

ثم نفّذ تحقق ما بعد الاستيراد:

```bash
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f db/imports/verify-official-opportunities-2026-10-17.sql
```

المتوقع في أول تشغيل لقاعدة خالية من التكرارات: ستة سجلات جديدة في `review`، مع مصادر رسمية ومعايير أهلية. إعادة التشغيل لا ينبغي أن تضاعف هذه السجلات. السجلات المتكررة الموجودة مسبقًا يتم تخطيها ولا تُعدّل أو تُثرى تلقائيًا؛ راجعها منفصلًا.

لا تنشر أي سجل تلقائيًا. قبل تحويل أي فرصة إلى `published`، راجع توفر البرنامج حاليًا، جغرافيا الأهلية، المبالغ، شروط التقديم وروابطه، ثم اعتمدها حسب عملية الموافقة في المشروع.

## 5. ربط API بعد التأكد من قاعدة دائمة

إذا كانت قاعدة البيانات هي مصدر بيانات التطبيق الحي، أضف `DATABASE_URL` في إعدادات Environment لخدمة `masar-startup-muhannad-api` داخل Render أو لدى مزود الاستضافة الفعلي، وليس داخل ملف الكود. استخدم عنوان الاتصال الخاص/الداخلي حين يدعم مزود الخدمة ذلك، واضبط `DATABASE_SSL=true` فقط حسب متطلبات TLS لدى المزود.

بعد الإعداد، افحص:
- `GET /health`: ينبغي أن يعرض `database: connected`.
- `GET /api/opportunities`: ينبغي أن يعرض `mode: database`. هذا المسار يعرض السجلات المنشورة والمعتمدة فقط، لذا قد لا تظهر المرشحات الستة الجديدة حتى يعتمدها مراجع.
